# C2 Data foundation

Status: draft, 2026-10-23

## Goal

Get the first real data into a local PostgreSQL database: all current Swiss
municipalities from the BFS register and their electricity prices from ElCom.
The import is repeatable, tested against a real database, and runs with one
command.

## Scope

- PostgreSQL in Docker Compose (`compose.yaml`), started with
  `docker compose up -d db`. Credentials only in `.env` (an `.env.example`
  is committed).
- `apps/api`: NestJS skeleton with TypeORM, connected to the database. It owns
  the schema: entities and migrations live here. No HTTP endpoint yet.
  - `nx run api:migrate` applies all migrations.
  - Migrations are generated by TypeORM, reviewed as SQL and committed.
  - New ADR 0009 "Database access with TypeORM".
- `apps/importer`: Python command-line job, managed with uv (Python version
  and lockfile), linted and formatted with ruff, type-checked with mypy,
  tested with pytest. Integrated into Nx with `lint`, `typecheck` and `test`
  targets so that `nx affected` and CI pick it up.
  - Started with `docker compose run --rm importer` (or locally with `uv run`).
  - The job never changes the schema (see ADR 0007).
- Data in the database:
  - All municipalities of the current BFS snapshot (key: BFS number), with
    name and canton. The canton is found through the district. BFS numbers
    are only unique together with their level (canton 1 is Zürich,
    municipality 1 is Aeugst am Albis).
  - ElCom tariffs for profile H4, tariff year 2027, product "standard",
    per grid operator and municipality: total price and its five parts
    (energy, grid usage, levies, grid surcharge, metering), in Rp./kWh.
    The total is stored as published by ElCom. ElCom rounds each value to
    three decimals, so the total may differ from the sum of the parts by
    up to 0.001. A larger difference means invalid data and stops the
    import.
  - Every ElCom municipality number must exist in the current BFS snapshot.
    If not, the import stops with a clear message. (For 2027 ElCom already
    uses the current list. Mapping merged municipalities comes when an
    older tariff year is needed.)
  - Municipalities with more than one grid operator: the average price is
    stored as well, with a flag "multiple operators".
  - Municipalities without ElCom data stay in the database with an empty
    price.
- Import behaviour:
  - Idempotent: running it twice gives the same result, no duplicates.
    Data for the tariff year is replaced.
  - All or nothing: the whole import runs in one transaction. On any error
    the previous data stays untouched and the job exits with a non-zero
    code and a clear message.
  - At the end it prints a summary: number of municipalities, number with a
    price, number without, number with several grid operators.
- Tests:
  - Unit tests (pytest) for parsing, canton lookup, the number check and
    averaging, using small fixture files with real, shortened responses
    from BFS and ElCom. Tests never call the real sources.
  - Integration test with Testcontainers: start a real PostgreSQL, apply the
    TypeORM migrations, run the import with the fixtures, check the result
    with SQL. Runs in CI.
- Data sources and licences are listed in the README (source attribution is
  required for BFS). ElCom data is "Open use" without required attribution
  (checked 2026-10-23); we name the source anyway.

## Data notes (checked 2026-10-23)

- BFS REST: `https://www.agvchapp.bfs.admin.ch/api/communes/snapshot?date=DD-MM-YYYY&useBfsCode=true`
  (checked 2026-10-26), CSV, 2110 municipalities (level 3), 144 districts
  (level 2), 26 cantons (level 1). Columns used: `HistoricalCode`,
  `BfsCode`, `Level`, `Parent`, `Name`, `ShortName` (canton abbreviation).
  `Parent` refers to the `HistoricalCode` of the level above, not to the
  `BfsCode`. `HistoricalCode` is only unique within a level (district Horgen
  and the municipality Vionnaz are both 10078), so lookups are per level
  (checked 2026-10-29).
- ElCom on LINDAS (SPARQL, `https://ld.admin.ch/query`), cube
  `https://energy.ld.admin.ch/elcom/electricityprice`: 2242 rows for H4,
  2027, "standard"; 2109 municipalities, 125 with several operators (up to
  four), 536 operators (numeric ids up to 904). Totals range from 10.6 to
  45.9 Rp./kWh, all values have at most three decimals. In 593 rows the
  total differs from the sum of the parts by 0.001 (checked 2026-10-26).
- ElCom dimensions map to our columns: `total` → `total`, `energy` →
  `energy`, `gridusage` → `grid_usage`, `charge` → `levies`, `aidfee` →
  `grid_surcharge`, `meteringrate` → `metering`. The operator id is the last
  path segment of the operator URI, its name is `schema:name`.

## Data model (decided 2026-10-26)

All names in `snake_case` (ADR 0009). Prices in Rp./kWh as `numeric(7,4)`:
exact decimals, enough for the three decimals from ElCom and a rounded
average.

- `canton`: `bfs_number` (primary key), `abbreviation` (e.g. "ZH"), `name`.
- `municipality`: `bfs_number` (primary key), `name`, `canton_bfs_number`
  (foreign key to `canton`).
- `grid_operator`: `elcom_id` (primary key), `name`.
- `tariff`: one row per grid operator, municipality and tariff year.
  `id` (primary key), `municipality_bfs_number`, `grid_operator_elcom_id`,
  `tariff_year`, `total`, `energy`, `grid_usage`, `levies`,
  `grid_surcharge`, `metering`. Unique on (municipality, grid operator,
  tariff year).
- `municipality_price`: one row per municipality and tariff year.
  Primary key (`municipality_bfs_number`, `tariff_year`), `average_total`,
  `multiple_operators`. A municipality without ElCom data has no row here.
- Districts are only used during the import to find the canton and are not
  stored.

## Out of scope

- HTTP endpoint, OpenAPI, Dockerfile for the API, images in GHCR (C3).
- Other tariff years, profiles and products than H4, 2027, "standard".
- Mapping of merged municipalities (not needed for 2027).
- Automatic schedule for the import (comes with Kubernetes, C11).
- Health insurance premiums and further data sets (C5).
- Historical versions of imported data.

## C2.5 Reading data (decided 2026-10-29)

Claude writes the code and explains it.

- HTTP with `requests` (plus `types-requests` for mypy). One fixed timeout
  (30 s), no retries: on any network error or non-2xx status the job stops
  with a clear message naming the source.
- Fetching and parsing are separate: parsers take the response text and
  return typed data, so the domain logic is tested without HTTP. The small
  fetch layer (URL, timeout, error status) is tested with `responses`.
- BFS: snapshot of the day the job runs, CSV. Structural check: required
  columns present, every municipality finds its district and canton,
  otherwise the import stops. No fixed counts.
- ElCom: SPARQL query sent to LINDAS, result as SPARQL JSON.
- Prices are `Decimal`, never `float`. Sum check: |total - sum of parts|
  must be at most 0.001, otherwise the import stops and names the
  municipality and grid operator.
- Number check: an ElCom municipality number missing in the BFS snapshot
  stops the import and names the number.
- Added after review (2026-10-29): an empty ElCom result stops the import
  (every per-row check passes on zero rows, and C2.6 would replace the
  tariff year with nothing). A duplicate (municipality, grid operator) pair
  in ElCom and a duplicate code within one BFS level also stop it.
- Average for municipalities with several grid operators: plain mean of the
  totals, rounded half up to four decimals; flag "multiple operators".
- `uv run importer` fetches both sources, runs all checks and prints the
  summary (municipalities, with price, without, with several operators).
  Exit code 0 on success, non-zero with a message otherwise. Nothing is
  written to the database yet (C2.6).
- Fixtures (real, shortened responses in `apps/importer/tests/fixtures/`):
  BFS with Aeugst am Albis (1) and Zürich (261) with their district and
  canton ZH, Siselen (499) with its district and canton BE; ElCom with one
  municipality with several grid operators and one row with a 0.001
  difference. Small error fixtures: unknown municipality number, difference
  of 0.002, BFS municipality without district, BFS district without canton.
  Added during implementation:
  Elsau (219, three grid operators), and Thalwil (141) with Vionnaz (6158)
  for the shared `HistoricalCode` 10078.

### C2.5 acceptance criteria

1. Unit tests cover: BFS parsing and canton lookup, BFS structural check,
   ElCom parsing, number check (criterion 5 above), sum check (0.001
   passes, 0.002 fails), averaging and flag (criterion 6 above), the fetch
   layer (timeout and error status).
2. `nx run-many -t lint typecheck test -p importer` passes; mypy strict
   without `Any` leaks from the parsers.
3. No test opens a real network connection.

### C2.5 end-to-end check

`uv run importer` in `apps/importer` with network access. Expected: exit
code 0 and a summary with about 2110 municipalities, about 2109 with a
price, about 125 with several grid operators. Siselen (499) counts as

## C2.6 Writing data (decided 2026-10-29)

Claude writes the code and explains it.

- Driver: psycopg 3 with plain SQL, no ORM in Python. The schema stays owned
  by the API migrations (ADR 0007, ADR 0009).
- Connection: the same variables as the API (`POSTGRES_HOST`,
  `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB`),
  with the same defaults (`localhost`, `5432`). A missing required value
  stops the job with a message naming the variable, before any data is
  fetched.
- Everything below runs in one transaction. On any error it is rolled back,
  the previous data stays untouched and the job exits with a non-zero code.
- Order of writes (all foreign keys are `NO ACTION`):
  1. Upsert (`INSERT … ON CONFLICT DO UPDATE`) cantons, municipalities and
     grid operators from the current data.
  2. Delete all `tariff` and `municipality_price` rows of tariff year 2027.
  3. Municipalities that are no longer in the BFS snapshot: delete their
     `tariff` and `municipality_price` rows (all years), then the
     municipalities themselves.
  4. Insert the `tariff` and `municipality_price` rows for 2027.
  5. Delete grid operators that have no tariff left.
- Rows of other tariff years are never touched, except for deleted
  municipalities (step 3). Cantons are only upserted, never deleted.
- Summary: as in C2.5, plus the number of deleted municipalities (decided
  2026-10-30).
- Integration test with Testcontainers (`testcontainers[postgres]`, same
  PostgreSQL image as `compose.yaml`): start the container, run
  `nx run api:migrate` with the container credentials, then run the import
  with the C2.5 fixtures (HTTP still mocked) and check the result with SQL.
  The CI job already has Node for the migration.
- Integration tests carry the pytest marker `integration`. A new Nx target
  `test-integration` runs only them. `test` and the pre-commit hook skip
  them, so they need no Docker. CI runs `test-integration` on every run.

### C2.6 acceptance criteria

1. After an import of the fixtures: Aeugst am Albis (1) and Zürich (261) in
   canton ZH with a price, Elsau (219) with the average and
   `multiple_operators`, Siselen (499) without a `municipality_price` row.
2. A second import gives exactly the same rows (idempotent).
3. A 2026 tariff of an existing municipality, inserted before the import,
   is still there afterwards.
4. A municipality inserted before the import that is not in the fixtures is
   deleted together with its prices of all years; the summary reports one
   deleted municipality.
5. A grid operator inserted before the import without any tariff is gone
   afterwards.
6. If the import fails after the first writes (e.g. a forced error before
   commit), the database is exactly as before.
7. A missing `POSTGRES_PASSWORD` stops the job with a non-zero code and a
   message naming the variable (unit test, no database).
8. `nx run-many -t lint typecheck test -p importer` passes without Docker;
   `nx run importer:test-integration` passes locally and in CI.

### C2.6 end-to-end check

`docker compose up -d db`, `nx run api:migrate`, then `uv run importer` in
`apps/importer` with the values from `.env`. Expected: exit code 0, summary
with about 2110 municipalities and 0 deleted. A second run gives the same
summary. With `psql`: `select count(*) from municipality` is about 2110.

## Acceptance criteria

1. `docker compose up -d db` starts PostgreSQL; `nx run api:migrate` creates
   all tables on an empty database.
2. `docker compose run --rm importer` imports real data and exits with code 0.
   The summary shows 2110 municipalities (status 2026-10-23), about 2109
   of them with a price.
3. Running the import a second time gives exactly the same row counts.
4. If a source is unreachable or returns invalid data, the job exits with a
   non-zero code and the data from the previous run is unchanged.
5. If the ElCom data contains a municipality number that is not in the BFS
   snapshot, the import stops with a non-zero code and names the number
   (covered by a unit test with fixtures).
6. A municipality with several grid operators has the average price and the
   flag "multiple operators" (covered by a unit test).
7. A municipality without ElCom data (in 2027: Siselen, BFS 499) exists with
   an empty price.
8. `nx run-many -t lint typecheck test` passes for `api`, `importer` and `web`;
   ruff, mypy and pytest run as part of it.
9. The Testcontainers integration test passes locally and in CI.
10. No credentials are committed; gitleaks stays green.
11. README lists the data sources with their attribution.

## End-to-end check

1. Fresh clone, `pnpm install`, copy `.env.example` to `.env`.
2. `docker compose up -d db`, then `nx run api:migrate`.
3. `docker compose run --rm importer`. Expected: exit code 0, summary with
   2110 municipalities.
4. With `psql`, look up Zürich (BFS 261, canton ZH) and Aeugst am Albis
   (BFS 1, canton ZH): both have a plausible price between 10 and 46 Rp./kWh.
   Siselen (BFS 499) has no price.
5. Run the import again. Expected: same counts.
6. Stop the database container (`docker compose stop db`) and run the import.
   Expected: non-zero exit code and a clear error message.
